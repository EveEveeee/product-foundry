# 关键产品决策

这些决策来自单用户需求讨论、实现检查和反例复验，主要体现我对范围、用户确认、文档版本与 Agent 执行边界的设计。当前不是广泛用户研究结论。证据标题与日期见[来源索引](provenance.md#证据索引)。

## 1. 先完成规划文档

首版需求规划原型以“生成可修改、保存和导出的 PRD 与技术方案”为终点。用户可以先输入模糊想法，不需要提前准备完整需求或掌握技术术语。

讨论采用推荐、理由和取舍说明，每轮最多提出三个关键问题。用户不知道如何选择时可以参考推荐；未接受的推荐仍保留为建议。自动开发目标产品、部署上线、模板市场和多用户协作不属于该原型的首版范围。

取舍是先验证需求讨论与文档交付是否可靠，避免一次扩展到完整开发平台。[依据：E01、E02]

## 2. 用户决定必须可追溯

| 信息类型 | 处理规则 |
| --- | --- |
| 用户明确决定 | 保留原话和来源，记录确认状态 |
| AI 推荐 | 展示理由与取舍，等待用户接受或修改 |
| 未知项与假设 | 显式标记，不自动写成已确认事实 |
| 明确排除项 | 作为后续生成的范围约束 |
| 冲突内容 | 展示冲突与来源，交给用户处理 |

“先按你推荐的做”只对应当时实际展示的一组建议。建议的 ID、版本和轮次形成接受范围，之后的新建议不能继承这次确认。资料中的要求也不能替代用户决定。[依据：E02、E03]

## 3. 生成完成不等于确认完成

需求规划原型将编辑草稿、保存版本与确认版本分开。缺少核心需求或存在未解决事项时，可以保留可读草稿，但不能直接标为已经确认。

技术方案绑定用户确认的 PRD 版本。新需求确认后，基于旧版的方案提示待更新，旧文档仍可查看。导出使用选定版本，保留来源关系，不在导出时重新润色内容。

AI 修改先显示前后差异，用户接受后进入草稿；手动编辑与已有版本不被静默覆盖。“交付就绪”只表示规划文档达到对应条件，不表示目标 Agent 已开发。[依据：E01、E03]

## 4. 用快照和状态保护恢复

生成任务记录启动时的输入和配置，避免用户中途修改后产生来源不明的文档。重复提交、停止、失败与重试分别有明确行为；失败保留已有文档，结果仍标明实际输入版本。

桌面工作台的模型比较单独处理提示词、材料、模型选择与结果草稿恢复。运行中离开页面需要选择继续还是停止；错误说明连接认证或配置等具体原因，并给出处理入口。模型比较使用同一份输入，但不据单个例子评出模型排名。[依据：E01、E06、E07]

## 5. 团队模型配置要明确

桌面工作台创建团队时，从已启用且可用的模型中解析默认模型。显式选择的模型不可用时提示检查配置，不静默换成另一模型；没有可用模型时阻止创建。

团队状态刷新不重复启动失败成员，重试由明确操作触发。团队成员的模型可以预览、编辑和刷新，让界面选择与后端保存结果一致。[依据：E06、E07]

## 6. 审查 Agent 先取证，再提交建议

独立 POC 使用 Pi 运行时和 MCP。Agent 读取项目记忆与 PRD，再依据反馈决定继续读取或检索，完成候选修订后调用校验与提交工具。

- 工具限定为项目记忆、文档读取、证据检索、修订校验和建议提交；限定测试资料范围。
- 暂时失败可重试一次；证据确实缺失时保留待确认，不猜测决定内容。
- 工具调用和模型轮数分别设预算，到达上限停止继续执行。
- `ready` 表示建议准备好；建议独立保存，原稿仍保留，是否应用由用户另行确认。

这部分验证工具反馈驱动的审查循环。需求规划原型的阶段生成流程与桌面助手协作分别描述，不将三者混称为已经集成的自主 Agent 系统。[依据：E09]
